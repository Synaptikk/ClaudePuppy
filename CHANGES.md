# CHANGES.md

Detailed log of the diagnosis and fixes in this patch. Written from a
troubleshooting session on 2026-07-10.

## Baseline environment

- **VDI:** Windows 11 Enterprise multi-session, FSLogix profile.
- **H:\ drive:** SMB share, `\\avdfsplteu2\codepuppy` (East US 2 region).
  Persists across VDI wipes.
- **C:\cp_venvs\`user`\:** Local disk. Wiped weekly by VDI imaging.
- **Base install:** ClaudePuppy VDI hybrid, per `setup_windows_vdi.txt` v9.

## Diagnosis timeline

### 1. Measured `apiKeyHelper` overhead

Claude Code's `settings.json` had:

```
"apiKeyHelper": "H:\\<user>\\.local\\bin\\get-puppy-token.cmd"
```

Claude Code invokes this on every API request. Measured baseline:

```powershell
Measure-Command { 1..5 | ForEach-Object { & 'H:\<user>\.local\bin\get-puppy-token.cmd' | Out-Null } }
# -> 4348 ms for 5 calls = ~870 ms / call
```

At 10+ tool calls per turn, that's 8+ seconds of pure token-lookup overhead
before Claude Code even starts thinking.

### 2. First hypothesis: `puppy.cfg` on H:\ is the bottleneck

The original helper `findstr`'d `puppy.cfg` (on H:\) on every call. I mirrored
the token to `%LOCALAPPDATA%\ClaudePuppy\puppy_token.txt` (local disk),
rewrote the helper to `type` the local file. Re-measured:

```
still ~1000 ms / call
```

Basically unchanged. The `puppy.cfg` read wasn't the bottleneck.

### 3. Second hypothesis: `cmd.exe` loading the .cmd from H:\

I copied the identical helper to `C:\Users\<user>\AppData\Local\ClaudePuppy\`
and timed it there:

```
55 ms / call
```

**18x speedup just from moving the batch file.** The bottleneck is `cmd.exe`
reading the `.cmd` file itself over SMB on every fork, not any command
inside the batch. The `puppy.cfg` optimization only matters as a secondary
win once the batch is local.

### 4. `set /p` vs `for /f` vs `type`

Along the way I burnt time on batch-language pitfalls worth flagging:

- **`set /p PT=<file`** truncates at ~1023 chars. `puppy_token` JWTs are
  ~2700+ chars. This silently produces a corrupt token.
- **`for /f "usebackq tokens=* delims=" %%a in ("file") do @echo %%a`** works
  correctly but adds ~1000 ms of overhead per invocation inside a batch, for
  reasons I didn't dig into (cmd's `for /f` machinery seems to shell out
  even for the file variant).
- **`type "file"`** just works and is essentially free. That's what the final
  helper uses.

### 5. Weekly wipe scope

The base installer's claim that "nothing lives on `C:\cp_venvs`, so the
weekly VDI wipe does NOT affect ClaudePuppy" is true for the **ClaudePuppy
launchers themselves** (sanitizer.py, wrappers, `claude-real.exe` all on
H:\) but misleading in aggregate:

- **Sanitizer venv:** Rebuilt automatically by `uv run --script` on first
  launch after a wipe (~30-60 s). No user action needed, just latency.
- **Code Puppy venv:** NOT auto-rebuilt. `C:\cp_venvs\<user>\code-puppy-venv\`
  is gone after a wipe. Code Puppy can't run until someone manually re-runs
  `setup_windows_vdi.txt`. Since Code Puppy is what refreshes the puppy_token
  JWT, this eventually blocks Claude Code auth (once the JWT expires).

## What changed

### `bin/claude-wrapper.ps1` (modified)

- Added a new section (1a) that on every wrapper launch:
  - Writes the current puppy_token to `%LOCALAPPDATA%\ClaudePuppy\puppy_token.txt`
    (with CRLF terminator, ~2733 bytes).
  - Overwrites `%LOCALAPPDATA%\ClaudePuppy\get-puppy-token.cmd` with a
    canonical, inlined-in-PS1 version of the fast helper. This makes the
    C:\ copy self-healing even if the user deletes it or edits it.
- Added a new section (1b) that migrates `settings.json`'s `apiKeyHelper`
  from the H:\ path to the C:\ path exactly once (no-op after the first run).
- No changes to the token expiry check, sanitizer prewarm loop, or claude-real
  invocation.

### `bin/get-puppy-token.cmd` (modified)

- Reads `%LOCALAPPDATA%\ClaudePuppy\puppy_token.txt` via `type` if present
  (~5 ms of actual work).
- Falls back to the original H:\ `findstr` on `puppy.cfg` if the cache is
  missing (safety net for cold-start / hand-deletion).
- The H:\ copy is now only used as a fallback; the C:\ copy that gets
  regenerated by `claude-wrapper.ps1` is the actual live path.

### `bin/sanitizer-prewarm.vbs` (new)

- Two-line VBS shim that runs `sanitizer-launcher.cmd` hidden (no visible
  console window) at logon.
- Registered in `HKCU\Software\Microsoft\Windows\CurrentVersion\Run` as
  `ClaudeSanitizerPrewarm`.
- If the sanitizer is already bound to 127.0.0.1:8787, uvicorn fails to
  bind and exits fast — safe no-op.

### `bin/ensure-code-puppy.ps1` (new)

- Fast-exits (~50 ms) when `C:\cp_venvs\<user>\code-puppy-venv\Scripts\code-puppy.exe`
  is present.
- Otherwise invokes `H:\<user>\.local\bin\setup-code-puppy.ps1` (a copy of
  `setup_windows_vdi.txt` renamed to a runnable extension) to rebuild the
  venv from the Walmart pypi mirror.

### `bin/code-puppy-prewarm.vbs` (new)

- Same pattern as sanitizer-prewarm.vbs, but for ensure-code-puppy.ps1.
- Registered as `ClaudePuppyEnsure`.

### `bin/register-run-keys.ps1` (new)

- Idempotent registration of both HKCU Run entries. Standalone, safe to
  re-run.

### `install-vdi-perf-patch.ps1` (new)

- One-shot idempotent patch installer. Deploys everything above, migrates
  settings.json, seeds the cache, copies `setup_windows_vdi.txt` into H:\
  as `setup-code-puppy.ps1`, and registers the Run keys.

## Performance verification

```powershell
# Cache-hit path (post-patch)
Measure-Command { 1..10 | ForEach-Object { & "$env:LOCALAPPDATA\ClaudePuppy\get-puppy-token.cmd" | Out-Null } }
# -> ~550 ms for 10 calls = ~55 ms / call

# End-to-end sanitizer roundtrip (unchanged)
Measure-Command { 1..5 | ForEach-Object { curl.exe -s -o $null http://127.0.0.1:8787/ } }
# -> ~380 ms for 5 calls = ~75 ms / call
```

Estimated real-world impact per Claude Code turn (assuming 10 API calls):

|                          | Before  | After   |
|--------------------------|---------|---------|
| Token helper overhead    | ~8.7 s  | ~0.55 s |
| Savings per turn         |         | ~8.15 s |
